# مِيثاق API

طبقة الـ Backend الخاصة بتسجيل الدخول والاشتراك والمصادقة الثنائية، مبنية لتعمل مباشرة فوق قاعدة البيانات الموجودة في `schema.sql`.

## التشغيل بأمر واحد عبر Docker (الطريقة الموصى بها)

```bash
cp .env.example .env      # ثم عدّل ANTHROPIC_API_KEY وVOYAGE_API_KEY بمفاتيح حقيقية إن أردت تجربة المحادثة/تحليل العقود
docker compose up --build
```

هذا يشغّل ثلاث خدمات معاً:
- **db**: PostgreSQL 16 مع pgvector، وينفّذ `schema.sql` تلقائياً عند أول تشغيل (لا حاجة لأي أمر يدوي).
- **api**: الخادم على المنفذ `4000` — جرّب: `curl http://localhost:4000/health`.
- **adminer**: أداة إدارة قاعدة بيانات بواجهة ويب على `http://localhost:8080` (اختر PostgreSQL، الخادم: `db`، المستخدم: `meethaq_app`).

لإيقاف كل شيء: `docker compose down` (البيانات تبقى محفوظة في volume باسم `meethaq_db_data`). لحذفها كلياً أضف `-v`.

## النشر على Render

المستودع يحتوي على `render.yaml` (Blueprint) ينشئ خدمة الـ API (Docker) وقاعدة PostgreSQL 16 معاً:

1. افتح: https://render.com/deploy?repo=https://github.com/a9a9a9li/-
2. اربط حساب GitHub إن طُلب، وأدخل `ANTHROPIC_API_KEY` و`VOYAGE_API_KEY` (اختياريان لـ `/health`)، ثم **Apply**.
3. بعد اكتمال النشر: `curl https://<اسم-الخدمة>.onrender.com/health`

مفاتيح JWT والتشفير تُولَّد تلقائياً، و`schema.sql` يُطبَّق تلقائياً عند أول تشغيل إذا كانت القاعدة فارغة.

## التشغيل اليدوي بدون Docker (بديل)

```bash
npm install
cp .env.example .env      # ثم عدّل القيم بمفاتيح حقيقية
# نفّذ schema.sql على قاعدة بيانات PostgreSQL فارغة
npm run dev
```

## تدفّق تسجيل الدخول (مصمّم عمداً على خطوتين)

1. `POST /auth/login` — بريد إلكتروني وكلمة مرور فقط. إن نجحا، يُعاد `mfaChallenge` (توكن صالح 5 دقائق) بدل جلسة كاملة.
2. `POST /auth/login/verify` — يُرسل معه `mfaChallenge` ورمز التطبيق (TOTP)، وعندها فقط يُصدر `accessToken` (15 دقيقة) و`refresh_token` كـ httpOnly cookie.

هذا يعني أن كلمة المرور وحدها **لا تكفي أبداً** لإصدار جلسة — وهو ما يطابق الشرط الأمني في تصميم المنصة.

## القضايا والمستندات والمواعيد (`/cases`, `/documents`, `/appointments`)

هذه هي المسارات التي تُغذّي فعلياً اللوحات الثلاث (المحامي/العميل/المسؤول):
- `/cases` تُرجع نتائج مختلفة تلقائياً حسب دور المستخدم (العميل يرى قضاياه فقط، عبر ربط `clients.user_id`).
- `/documents` لا تُظهر للعميل إلا مستنداً بحالة `visible_to_client = true`، ومشاركة أي مستند تُرفض ما لم يكن `approved` مسبقاً — نفس قيد "لا اعتماد بلا محامٍ" مطبَّق هنا أيضاً.
- كل عملية إنشاء أو تعديل تُسجَّل في `audit_logs` تلقائياً.

## المحادثة القانونية وتحليل العقود (`/chat/ask`, `/contracts/analyze`)

تم بناء المسارين بنمط RAG فعلي: استرجاع من `legal_texts` أولاً عبر بحث دلالي (pgvector)، ثم تمرير النصوص المسترجَعة فقط إلى Claude مع تعليمات صريحة بعدم الإجابة خارجها. تحليل العقود يُخرج نتائج JSON منضبطة تُخزَّن في `contract_risk_findings`، والمستند يبقى `pending_review` حتى يعتمده محامٍ صراحة عبر `/contracts/:id/approve`.

**ما لا يمكن توفيره هنا وهو خارج نطاق الكود نفسه:**
- **تعبئة `legal_texts` الفعلية**: يتطلب ترخيصاً أو اتفاقاً مع الجهة الرسمية الناشرة للتشريعات، وهذه خطوة قانونية/تعاقدية لا برمجية.
- **دقة التصنيف القانوني**: مهما كانت جودة النموذج، النتائج تبقى "أولية" وتتطلب مراجعة محامٍ قبل الاعتماد — هذا مطبَّق كقيد في الكود (`pending_review`) وليس مجرد توصية.
- استخراج نص العقد من ملف PDF/Word (OCR/parsing) غير مبني هنا؛ المسار يستقبل نصاً جاهزاً.

## نقاط يجب على فريق التطوير مراجعتها قبل الإنتاج

- استبدال جميع قيم `.env.example` بمفاتيح عشوائية حقيقية، وعدم إبقائها بالقيم الافتراضية.
- ضبط `NODE_ENV=production` لتفعيل `secure cookies` و`SSL` على اتصال قاعدة البيانات.
- مراجعة قانونية لسياسة الخصوصية وشروط الاستخدام قبل ربطهما بصفحة الاشتراك الفعلية.
- إضافة مسارات لاحقة (القضايا، المستندات، الفوترة) بنفس نمط `withFirmContext` لضمان استمرار عزل بيانات كل مكتب.
